# Redis Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A password-protected, deliberately ephemeral Redis cache whose
credential is generated inside Vault, delivered by VSO, and absent from the pod
spec, the process list and the environment — with eviction configured so the
cache evicts instead of being OOM-killed.

**Architecture:** A plain Deployment on `redis:8.2-alpine` with **no volume of
any kind**. A ConfigMap holds `redis.conf`; its last line `include`s a one-line
file that VSO renders from Vault KV into Secret `redis-credentials`. That
indirection exists so the password never becomes a command-line flag or an
environment variable.

**Tech Stack:** k3s v1.36.4+k3s1, Argo CD v3.5.2, Vault 2.0.4, VSO 1.5.1,
Redis 8.2.9 (`redis:8.2-alpine`).

**Spec:** `docs/superpowers/specs/2026-09-16-redis-design.md`

## Global Constraints

- **Never run `git push`.** The user reserves all pushes. Commit locally, print
  the exact push command, and wait.
- **`kubectl` needs a group wrapper on this host:** `sg k3s-admin -c '...'`.
  Nested quoting inside it is fragile — for anything multi-line, write a script
  to the scratchpad and run that.
- **Commands the user must edit and run must be shell-safe as written.** Never
  use `<angle brackets>` as a placeholder; `<` is a shell redirection and has
  broken this user's shell twice. Keep such commands on one line.
- **No credential may become a command argument.** Use the `key=@<path>` form
  the unsealer and `configure-vault.sh` already use, so only a filename appears
  in `ps`.
- **The password is never printed, echoed, or pasted into the conversation.**
- **Never grep `ps` output for the password.** The pattern lands in the grep's
  own argv and `ps` matches the grep itself, reporting a leak that is not
  there. Read the full `ps` output instead. This was hit twice while probing.
- **Image pinned to `redis:8.2-alpine`.** No `latest`, ever.
- **No PVC, no `volumeClaimTemplates`, no persistence.** `save ""` and
  `appendonly no`. If this phase creates a PVC, it has gone wrong.
- **Sync waves after this plan:** `argocd` -1, `namespaces` 0,
  `ingress-operator` 2, `vault` 10, `vso-operator` 21, `ingress-config` 21,
  `vso-config` 22, `postgres` 23, **`redis` 23**.
- **A directory used as an Argo CD `path` may contain only valid manifests.**
- **Argo CD reporting Synced/Healthy proves only what it applied.** Every
  verification asserts on running state — `status.resources`, a live object, an
  actual command against the running server.
- Argo CD polls every 3 minutes. Poll for existence before `kubectl wait`.

- [ ] **Step 3: Extend the ceremony script**

Append to `platform/vault/configure-vault.sh`, immediately before the final
`echo "==> done"` line. This mirrors the Postgres block directly above it:

```sh
echo "==> seeding homelab/redis"
if vault kv get homelab/redis >/dev/null 2>&1; then
  echo "    already present, leaving the credential alone"
else
  # Generated here and never displayed, exactly as the postgres block above.
  #
  # Alphanumeric only. Redis stores requirepass verbatim and would accept
  # anything, but clients build redis://:password@host URLs, where a / or @
  # breaks parsing in ways that surface far from the cause.
  #
  # Written to a file so that only the FILENAME becomes an argument -- a
  # password on a command line is visible in `ps`.
  PWFILE=$(mktemp)
  trap 'rm -f "$PWFILE"' EXIT
  head -c 256 /dev/urandom | tr -dc 'A-Za-z0-9' | head -c 32 > "$PWFILE"
  vault kv put homelab/redis username=default password=@"$PWFILE" >/dev/null
  rm -f "$PWFILE"
  echo "    generated"
fi

echo "==> policy vso-redis-read"
# The data/ segment is REQUIRED and is not a typo -- see the note on
# vso-canary-read above.
vault policy write vso-redis-read - <<'POLICY'
path "homelab/data/redis" {
  capabilities = ["read"]
}
POLICY

echo "==> role vso-redis"
# bound_service_account_names must match the ServiceAccount created in
# platform/databases/redis/config/vault-secrets.yaml, and audience must match
# that file's VaultAuth spec.kubernetes.audiences.
vault write auth/kubernetes/role/vso-redis \
    bound_service_account_names=redis \
    bound_service_account_namespaces=databases \
    audience=vault \
    token_policies=vso-redis-read \
    ttl=1h
```

`username=default` is not decorative: `default` is the actual Redis 6+ ACL user
that `requirepass` sets the password for. A client connecting with
`redis://:password@host` authenticates as `default`. Storing it makes the KV
entry self-describing and matches the shape of `homelab/postgres`.

- [ ] **Step 1: Create the Vault objects**

Create `platform/databases/redis/config/vault-secrets.yaml`. Note there is
**no `VaultConnection` here** — `databases` already has one, created by
PostgreSQL in phase 18, and a second one with the same name in the same
namespace would collide:

```yaml
# Redis's credential path: Vault KV -> VSO -> Secret -> a config-file include.
#
# There is deliberately NO VaultConnection in this file. Namespace `databases`
# already has one named `vault`, created with PostgreSQL in phase 18, and a
# VaultConnection is namespace-scoped state that both consumers can reference.
# The ServiceAccount, VaultAuth and VaultStaticSecret below MUST be per-consumer
# -- the VaultAuth CRD requires its ServiceAccount to live in the consuming
# Secret's namespace, and this one authenticates as a different Vault role.
---
# The identity Vault trusts. Its name must match bound_service_account_names
# in platform/vault/configure-vault.sh.
apiVersion: v1
kind: ServiceAccount
metadata:
  name: redis
  namespace: databases
---
apiVersion: secrets.hashicorp.com/v1beta1
kind: VaultAuth
metadata:
  name: redis
  namespace: databases
spec:
  # Reuses the VaultConnection PostgreSQL created in this namespace.
  vaultConnectionRef: vault
  method: kubernetes
  mount: kubernetes
  kubernetes:
    # role and audiences must both match platform/vault/configure-vault.sh.
    # A mismatch in either is a permission denial that names neither side,
    # while Argo CD reports everything Synced.
    role: vso-redis
    serviceAccount: redis
    audiences:
      - vault
---
apiVersion: secrets.hashicorp.com/v1beta1
kind: VaultStaticSecret
metadata:
  name: redis-credentials
  namespace: databases
spec:
  vaultAuthRef: redis
  mount: homelab
  type: kv-v2
  path: redis
  refreshAfter: 60s
  destination:
    name: redis-credentials
    create: true
    transformation:
      # Drop VSO's verbatim KV JSON. Without this the Secret carries the
      # password twice -- once parsed, once inside _raw -- widening what a
      # `kubectl get secret -o yaml`, an Argo CD resource view or an etcd
      # backup exposes. The two Secrets created before this one still carry
      # _raw; that is a known gap recorded in the root README, and fixing
      # them is deliberately not part of this phase.
      excludeRaw: true
      templates:
        # Renders the ENTIRE contents of a Redis config fragment. The
        # Deployment mounts this one key as a file and redis.conf includes it,
        # so the password reaches the server without ever being a flag or an
        # environment variable.
        requirepass.conf:
          text: |
            requirepass {{ get .Secrets "password" }}
```

- [ ] **Step 2: Create the cache itself**

Create `platform/databases/redis/config/redis.yaml`:

```yaml
# Redis 8.2 as a CACHE -- phase 19, the cache branch of the roadmap's two.
#
# There is no PVC, no volumeClaimTemplate and no persistence. `save ""` and
# `appendonly no` disable both on-disk paths, and readOnlyRootFilesystem means
# a manual BGSAVE cannot write anything. It is the container, not this comment,
# that stops anyone treating this as durable storage. If a future phase needs
# persistence, that is a deliberate change here, not an accident.
#
# NOTE: BGSAVE still REPLIES "Background saving started" -- it is asynchronous,
# so the reply is not the result. The refusal shows up in INFO persistence as
# rdb_last_bgsave_status:err and in the log as "Read-only file system".
# Anyone auditing this by reading BGSAVE's reply will reach the wrong
# conclusion. See platform/databases/redis/README.md.
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: redis-config
  namespace: databases
data:
  redis.conf: |
    # Tuning lives here, in git, readable in a diff. The credential does not.
    #
    # maxmemory is the SAFETY MECHANISM, not tuning. A cache given a container
    # memory limit but no maxmemory does not start evicting as it fills -- it
    # grows until the kernel OOM-kills it, and Kubernetes restarts it into the
    # same trajectory. allkeys-lru is what turns that loop into eviction.
    # 128mb sits at half the 256Mi container limit on purpose: maxmemory bounds
    # the DATASET, while RSS runs higher from allocator fragmentation and from
    # the four modules Redis 8 auto-loads (~22MiB at idle, measured).
    maxmemory 128mb
    maxmemory-policy allkeys-lru

    # Both persistence paths off. See the header comment.
    save ""
    appendonly no

    # MUST BE THE LAST LINE. Redis applies directives in read order and a later
    # one wins, so an include placed higher could have its requirepass silently
    # overridden by a following line -- in the direction of NO password.
    # The file itself is rendered by VSO from Vault; see vault-secrets.yaml.
    include /etc/redis/secret/requirepass.conf
---
apiVersion: v1
kind: Service
metadata:
  name: redis
  namespace: databases
spec:
  # A normal ClusterIP, unlike PostgreSQL's headless Service -- this is a
  # Deployment with no stable network identity to preserve. No Ingress: the
  # Redis wire protocol is not HTTP and does not belong behind the tailnet
  # proxy.
  selector:
    app: redis
  ports:
    - name: redis
      port: 6379
      targetPort: 6379
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis
  namespace: databases
spec:
  replicas: 1
  strategy:
    # Recreate, not RollingUpdate: a rolling update would briefly run two
    # caches, doubling the memory footprint on a host that is also a
    # workstation and a game server. There is no data to keep available
    # during the gap -- a cold cache is the normal cost of a restart here.
    type: Recreate
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      serviceAccountName: redis
      securityContext:
        # Probed from the image on 2026-09-16: the redis user is uid 999,
        # gid 1000 -- ASYMMETRIC, not the 999/999 usually assumed. (Phase 18
        # found the mirror image: postgres is 70/70, not the 999 everyone
        # expects. Neither image matches folklore.)
        #
        # fsGroup is set even though there is no PVC: it governs the SECRET
        # volume too, making requirepass.conf group-readable by 1000 so uid
        # 999 can read it. Without it the file is root-owned and mode 0440
        # would lock redis out of its own password at startup.
        runAsNonRoot: true
        runAsUser: 999
        runAsGroup: 1000
        fsGroup: 1000
      containers:
        - name: redis
          image: redis:8.2-alpine
          # One argument: the config file. The password is NOT here, and that
          # is the whole design -- see spec R5.
          args:
            - /etc/redis/redis.conf
          ports:
            - name: redis
              containerPort: 6379
          securityContext:
            # Nothing is ever written to disk, so the root filesystem can be
            # read-only. This is what makes BGSAVE unable to write -- note it
            # still reports success to the client; see the header comment.
            readOnlyRootFilesystem: true
            allowPrivilegeEscalation: false
            capabilities:
              drop:
                - ALL
          resources:
            requests:
              cpu: 25m
              memory: 64Mi
            limits:
              # Twice maxmemory. The gap is headroom so that eviction, not the
              # OOM killer, is the thing that reacts first as the cache fills.
              memory: 256Mi
          volumeMounts:
            - name: config
              mountPath: /etc/redis/redis.conf
              subPath: redis.conf
              readOnly: true
            - name: credential
              mountPath: /etc/redis/secret
              readOnly: true
          readinessProbe:
            exec:
              # NOT a bare `redis-cli ping`. With requirepass set, that prints
              # "NOAUTH Authentication required." and STILL EXITS 0 -- measured
              # 2026-09-16 -- so it is a probe that can never fail. Matching
              # the response text instead needs no password: NOAUTH is a
              # SUCCESS condition here, proving the server is listening,
              # speaking the protocol, and enforcing auth. Against a dead port
              # redis-cli prints "Connection refused" and matches neither.
              command:
                - sh
                - -c
                - redis-cli ping 2>&1 | grep -qE 'PONG|NOAUTH'
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            exec:
              command:
                - sh
                - -c
                - redis-cli ping 2>&1 | grep -qE 'PONG|NOAUTH'
            initialDelaySeconds: 15
            periodSeconds: 20
            timeoutSeconds: 5
            # Deliberately tolerant, matching PostgreSQL's reasoning: this host
            # has a recorded history of probe timeouts under memory pressure
            # (troubleshooting entries 4 and 10). Killing a cache because the
            # host was briefly busy is worse than waiting.
            failureThreshold: 6
      volumes:
        - name: config
          configMap:
            name: redis-config
        - name: credential
          secret:
            secretName: redis-credentials
            # Only the rendered config fragment is projected. Without `items`
            # the username and password keys would also appear as files here,
            # which nothing reads -- fewer copies of a credential on disk is
            # strictly better.
            items:
              - key: requirepass.conf
                path: requirepass.conf
            defaultMode: 0440
```

- [ ] **Step 3: Add troubleshooting entry 13**

`docs/troubleshooting.md` currently ends at entry 12. Add `## 13. Redis will
not start, or refuses the password`, covering the failure modes this design
actually has:

- **Pod in `CrashLoopBackOff` with a config-file error** — the `include` target
  is missing or unreadable. Check the Secret exists and carries the
  `requirepass.conf` key, then check the file's group is `1000`
  (`kubectl -n databases exec deploy/redis -- ls -l /etc/redis/secret/`).
  The `fsGroup` is what makes it readable by uid 999.
- **Clients get `NOAUTH` with what they believe is the right password** — the
  Vault value was rotated but the server was not restarted. See the rotation
  section of the component README.
- **Clients connect with NO password** — the `include` is not taking effect, or
  was moved off the last line of `redis.conf` and overridden. Verify with
  `redis-cli -e ping` from a separate pod; note that **without `-e`,
  `redis-cli` exits 0 even on `NOAUTH`**, which is why a casual check can
  appear to pass.
- **The pod is Ready but Redis is broken** — someone replaced the probe with a
  bare `redis-cli ping`, which exits 0 on `NOAUTH`. Compare against
  `platform/databases/redis/config/redis.yaml`.
- **"I took a backup" — no, you did not.** `BGSAVE` replies `Background saving
  started` even though the read-only filesystem refuses the write. Check
  `INFO persistence` → `rdb_last_bgsave_status:err` and the pod log's `Failed
  opening the temp RDB file ... Read-only file system`. This cache has no
  backups by design; if you need a durable copy, the datastore is the wrong
  one, not the flags.
- **Evictions or OOMKills under load** — check
  `redis-cli info memory` and `kubectl describe pod` for `OOMKilled`. If
  `maxmemory` reads `0`, the ConfigMap is not reaching the server; if it reads
  `134217728` and the container is still OOMKilled, the RSS-vs-dataset gap is
  too small and the limit needs raising, not `maxmemory`.
