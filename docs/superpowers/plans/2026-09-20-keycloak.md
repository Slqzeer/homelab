# Keycloak and Centralized Authentication Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Keycloak 26.7.4 owning a `homelab` realm, storing its state in the phase-18 PostgreSQL, reached only over the tailnet, taking every credential from Vault — with Grafana logging in through it as the first real OIDC client, and PostgreSQL fenced by the NetworkPolicy its first application consumer finally justifies.

**Architecture:** Plain manifests (no chart, no operator) in a new `keycloak` namespace, one Argo CD Application at **wave 24** beside `beacon` and `monitoring-config`. The realm is JSON in git applied by `--import-realm` — reproducible, not reconciled. The `keycloak` PostgreSQL role and database are created by an Argo CD Sync-hook Job in `databases`, copying the phase-22 exporter Job exactly. Grafana's OIDC client secret is generated by Keycloak and pasted once into Vault; `configure-vault.sh` seeds a placeholder first, which is what stops wave 23 and wave 24 deadlocking on each other.

**Tech Stack:** `quay.io/keycloak/keycloak:26.7.4`, PostgreSQL 18.6 (already installed), Vault + Vault Secrets Operator (already installed), kube-prometheus-stack 91.4.1 (already installed), Tailscale operator 1.102.3, k3s v1.36.4+k3s1, containerd 2.3.4-k3s1.36, Argo CD, Docker (for offline realm validation).

**Spec:** `docs/superpowers/specs/2026-09-20-keycloak-design.md`

## Global Constraints

- **Never `git push`.** Commit, then hand the push command to the operator. A push to `main` is a deploy: Argo CD reconciles `main` with `selfHeal: true`.
- **Work on `main`.** Nothing reconciles a feature branch into this cluster.
- **Validate with the real CI command**, never a bare local `kubeconform`. Local kubeconform without both `-schema-location` flags silently skips every CRD and has already hidden a Critical finding in this repository. The exact commands are in Task 1, Step 5.
- **Pin every version exactly.** `quay.io/keycloak/keycloak:26.7.4`, `postgres:18.6-alpine` for the Job. No `latest`, no ranges, no floating `26.7`.
- **Never add a `-ignore-filename-pattern` to `validate.yaml`.** This phase needs no CI change (spec §13). `NetworkPolicy` is a core kind and validates against the default schema; the realm JSON lives inside a ConfigMap and is opaque to kubeconform by design, which is why Task 4 validates it with a real Keycloak instead.
- **`yamllint --strict`, line length max 100, and `.github/` is the only exemption.** The realm JSON is embedded in a YAML block scalar, so its effective line length is the JSON line plus four spaces of indent. Every JSON line must stay at or under 92 characters. Arrays get one element per line.
- **Every manifest that lands outside its Application's destination namespace carries an explicit `metadata.namespace`.** This phase writes into `keycloak`, `databases` and `monitoring` from three different Applications.
- **Every new `VaultStaticSecret` carries `excludeRaw: true`** (spec K17). The repository already tracks two Secrets that keep the duplicate `_raw` key; this phase adds none.
- **`kubectl` needs the `k3s-admin` group.** If a command returns a permissions error, prefix it: `sg k3s-admin -c '…'`.
- **`sudo` has no TTY in this session.** Any host-root step is an operator hand-off, not something to attempt. No task here needs one: `/backups` is mode 0777.
- **`yamllint` runs through Docker, not `pip`.** This host has no `ensurepip`. The exact command is in Task 1, Step 5, pinned to the `yamllint==1.38.0` the workflow uses.
- **Never hand the operator a command containing `<angle brackets>` or a line continuation.** `<` is a shell redirection; a pasted placeholder truncates the file it redirects from. Every operator command in this plan is runnable verbatim.
- **No secret ever becomes a command-line argument.** Passwords go to a file and are passed as `key=@/path`, the idiom `configure-vault.sh` already uses, because argv is visible in `ps`.

### One deviation from the spec, and why

Spec §6 places the NetworkPolicy at `platform/keycloak/config/networkpolicy.yaml`. **This plan does not.** A policy shipped by the `keycloak` Application is owned by one of the database's clients: retiring Keycloak would, by the root README's removal procedure, take the fence around PostgreSQL with it. The policy protects the database, so it ships with the database — `postgres` (wave 23) carries the namespace default-deny and the Postgres rules, `redis` (wave 23) carries the Redis rules. Both are at wave 23, so the fence exists before Keycloak at wave 24 ever connects, and the `keycloak` allow-rule simply matches nothing until then.

Task 8, Step 9 updates spec §6 to match, so the two documents do not contradict each other.

- [ ] **Step 2: Append the three credential blocks to `configure-vault.sh`**

Insert before the final `echo "==> done"` line:

```sh
echo "==> seeding homelab/keycloak"
if vault kv get homelab/keycloak >/dev/null 2>&1; then
  echo "    already present, leaving the credential alone"
else
  # The BREAK-GLASS admin of the `master` realm, and nothing else. Humans
  # live in the `homelab` realm; this account exists to recover them.
  #
  # Generated here and never displayed, exactly as the postgres, redis,
  # nexus and grafana blocks above.
  #
  # Alphanumeric only -- this password is pasted into a browser login.
  #
  # IMPORTANT ASYMMETRY: KC_BOOTSTRAP_ADMIN_PASSWORD is honoured only when
  # no admin exists. Unlike homelab/postgres, whose Sync-hook Job runs
  # ALTER ROLE on every sync, rewriting this value does NOT change the live
  # password. Rotate in Keycloak first, then update Vault to match.
  # See platform/keycloak/README.md.
  PWFILE=$(mktemp)
  trap 'rm -f "$PWFILE"' EXIT
  head -c 256 /dev/urandom | tr -dc 'A-Za-z0-9' | head -c 32 > "$PWFILE"
  vault kv put homelab/keycloak username=admin password=@"$PWFILE" >/dev/null
  rm -f "$PWFILE"
  echo "    generated"
fi

echo "==> seeding homelab/keycloak-db"
if vault kv get homelab/keycloak-db >/dev/null 2>&1; then
  echo "    already present, leaving the credential alone"
else
  # The PostgreSQL login Keycloak connects with. Read in TWO namespaces:
  # `keycloak` (the Deployment) and `databases` (the Sync-hook Job whose
  # ALTER ROLE pushes this value into the database on every sync).
  #
  # Alphanumeric only: this value lands in a JDBC URL, where a / or @
  # breaks parsing in ways that surface far from the cause.
  PWFILE=$(mktemp)
  trap 'rm -f "$PWFILE"' EXIT
  head -c 256 /dev/urandom | tr -dc 'A-Za-z0-9' | head -c 32 > "$PWFILE"
  vault kv put homelab/keycloak-db username=keycloak password=@"$PWFILE" >/dev/null
  rm -f "$PWFILE"
  echo "    generated"
fi

echo "==> seeding homelab/keycloak-grafana"
if vault kv get homelab/keycloak-grafana >/dev/null 2>&1; then
  echo "    already present, leaving the value alone"
else
  # A PLACEHOLDER, and deliberately so. Keycloak generates the real client
  # secret when it imports the realm; a human then overwrites this value.
  # See platform/keycloak/README.md.
  #
  # This block exists to break a REBUILD DEADLOCK, not to supply a working
  # credential. Grafana (wave 23) reads this Secret through envValueFrom.
  # A Secret that does not exist leaves the pod in
  # CreateContainerConfigError, so `monitoring` never goes Healthy, so
  # NOTHING AT WAVE 24 SYNCS -- including the Keycloak that is the only
  # thing able to produce the real value. Grafana would wait on Keycloak
  # and Keycloak on Grafana, with nothing anywhere naming identity as the
  # cause.
  #
  # Seeded, the failure degrades to `invalid_client` on the SSO button
  # while Grafana's local admin form keeps working.
  PWFILE=$(mktemp)
  trap 'rm -f "$PWFILE"' EXIT
  head -c 256 /dev/urandom | tr -dc 'A-Za-z0-9' | head -c 32 > "$PWFILE"
  vault kv put homelab/keycloak-grafana clientSecret=@"$PWFILE" >/dev/null
  rm -f "$PWFILE"
  echo "    generated placeholder -- Keycloak's real secret replaces it"
fi

echo "==> policy vso-keycloak-read"
# Grants BOTH paths the Keycloak pod needs, so its one ServiceAccount needs
# one role. The data/ segment is REQUIRED and is not a typo -- see the note
# on vso-canary-read above.
vault policy write vso-keycloak-read - <<'POLICY'
path "homelab/data/keycloak" {
  capabilities = ["read"]
}

path "homelab/data/keycloak-db" {
  capabilities = ["read"]
}
POLICY

echo "==> role vso-keycloak"
# bound_service_account_names must match the ServiceAccount created in
# platform/keycloak/config/vault-secrets.yaml, and audience must match that
# file's VaultAuth spec.kubernetes.audiences.
vault write auth/kubernetes/role/vso-keycloak \
    bound_service_account_names=keycloak \
    bound_service_account_namespaces=keycloak \
    audience=vault \
    token_policies=vso-keycloak-read \
    ttl=1h

echo "==> policy vso-keycloak-db-read"
# Narrower than vso-keycloak-read on purpose: the Job in `databases` needs
# the database login and must not see the Keycloak admin credential.
vault policy write vso-keycloak-db-read - <<'POLICY'
path "homelab/data/keycloak-db" {
  capabilities = ["read"]
}
POLICY

echo "==> role vso-keycloak-db"
# A SECOND role rather than adding `databases` to vso-keycloak's namespaces.
# Vault's kubernetes auth matches the CROSS-PRODUCT of
# bound_service_account_names and bound_service_account_namespaces, so one
# role naming both SAs and both namespaces would additionally authorize
# `keycloak` in `databases` and `keycloak-db` in `keycloak` -- two
# identities nobody intended, and a widening no manifest comment reveals.
#
# bound_service_account_names must match the ServiceAccount created in
# platform/keycloak/config/database-job.yaml.
vault write auth/kubernetes/role/vso-keycloak-db \
    bound_service_account_names=keycloak-db \
    bound_service_account_namespaces=databases \
    audience=vault \
    token_policies=vso-keycloak-db-read \
    ttl=1h
```

```yaml
# VaultAuth -- the vso-keycloak-read policy grants both paths, so no second

# different ServiceAccount in a different namespace; it lives in
```

```yaml
# The `keycloak` PostgreSQL role and database, and the credential wiring
# that lives in `databases` rather than `keycloak`.
#
# This file lands OUTSIDE its Application's destination namespace, so every
# object below states `namespace: databases` explicitly. That is the same
# arrangement monitoring-config uses to write into four namespaces.
#
# The role is created by an Argo CD Sync HOOK, not a plain Job, for the
# reason platform/nexus/config/bootstrap-job.yaml sets out: a Job is
# immutable, so re-applying an unchanged one does nothing at all, and a
# changed script would never reach the cluster.
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: keycloak-db
  namespace: databases
---
apiVersion: secrets.hashicorp.com/v1beta1
kind: VaultAuth
metadata:
  name: keycloak-db
  namespace: databases
spec:
  # Reuses the VaultConnection PostgreSQL created in this namespace, the
  # way redis and postgres-exporter do. A second VaultConnection here would
  # be a duplicate pointing at the same address.
  vaultConnectionRef: vault
  method: kubernetes
  mount: kubernetes
  kubernetes:
    role: vso-keycloak-db
    serviceAccount: keycloak-db
    audiences:
      - vault
---
apiVersion: secrets.hashicorp.com/v1beta1
kind: VaultStaticSecret
metadata:
  name: keycloak-db
  namespace: databases
spec:
  vaultAuthRef: keycloak-db
  mount: homelab
  type: kv-v2
  path: keycloak-db
  refreshAfter: 60s
  destination:
    name: keycloak-db
    create: true
    transformation:
      excludeRaw: true
---
apiVersion: batch/v1
kind: Job
metadata:
  name: keycloak-database
  namespace: databases
  annotations:
    argocd.argoproj.io/hook: Sync
    argocd.argoproj.io/hook-delete-policy: BeforeHookCreation
spec:
  backoffLimit: 2
  # A Sync hook that never ends stalls the whole Argo CD sync.
  activeDeadlineSeconds: 300
  template:
    metadata:
      labels:
        # Selected by the NetworkPolicy in
        # platform/databases/postgres/config/networkpolicy.yaml. Without
        # this label the hook cannot reach 5432 once default-deny lands,
        # and the failure appears at the NEXT sync, arbitrarily far from
        # whatever commit caused it.
        job: postgres-client
    spec:
      serviceAccountName: keycloak-db
      restartPolicy: Never
      containers:
        - name: psql
          image: postgres:18.6-alpine
          env:
            - name: PGHOST
              value: postgres.databases.svc.cluster.local
            - name: PGUSER
              value: postgres
            - name: PGPASSWORD
              valueFrom:
                secretKeyRef:
                  name: postgres-credentials
                  key: password
            - name: KEYCLOAK_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: keycloak-db
                  key: password
          command:
            - /bin/sh
            - -c
            - |
              set -eu
              # Idempotent by construction: CREATE ROLE and CREATE DATABASE
              # are each guarded by a probe, and the ALTER runs
              # unconditionally so a rotated password in Vault reaches the
              # database on the next sync.
              until pg_isready -q; do
                echo "waiting for postgres"; sleep 2
              done
              if psql -tAc \
                "SELECT 1 FROM pg_roles WHERE rolname='keycloak'" \
                | grep -q 1; then
                echo "role keycloak exists"
              else
                psql -v ON_ERROR_STOP=1 -c "CREATE ROLE keycloak LOGIN"
                echo "role keycloak created"
              fi
              # The password is passed through a psql variable, never
              # interpolated into the SQL text, so it cannot reach a log or
              # the process list.
              #
              # This goes through stdin, not -c: psql does not expand -v
              # variables inside a -c command string, so `-c "... :'pw'"`
              # sends the six literal characters `:'pw'` to the server and
              # fails with a syntax error. Piped via a quoted heredoc, the
              # shell leaves :'pw' untouched and psql itself expands it.
              psql -v ON_ERROR_STOP=1 -v pw="$KEYCLOAK_PASSWORD" <<'SQL'
              ALTER ROLE keycloak WITH PASSWORD :'pw';
              SQL
              if psql -tAc \
                "SELECT 1 FROM pg_database WHERE datname='keycloak'" \
                | grep -q 1; then
                echo "database keycloak exists"
              else
                # CREATE DATABASE cannot run inside a transaction block,
                # which is why it is a separate -c invocation rather than
                # another statement in the heredoc above.
                psql -v ON_ERROR_STOP=1 \
                  -c "CREATE DATABASE keycloak OWNER keycloak"
                echo "database keycloak created"
              fi
              echo "done"
          resources:
            requests:
              cpu: 10m
              memory: 32Mi
            limits:
              memory: 64Mi
```
