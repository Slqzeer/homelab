# Vault Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A persistent, automatically-unsealing HashiCorp Vault at
`https://vault.taildf6cd4.ts.net`, reconciled by Argo CD, with a verified
snapshot procedure and a documented recovery path.

**Architecture:** Vault chart 0.34.1 as a single-replica StatefulSet using
Raft integrated storage on a local-path PVC. A small helper Deployment,
running the same Vault image, polls the seal status and unseals from keys
mounted out of a hand-created Secret. Storage is proven with a probe before
Vault is installed, because no PVC has ever existed on this cluster.

**Tech Stack:** k3s v1.36.4+k3s1, Argo CD 3.5.2, Vault chart 0.34.1 /
Vault 2.0.4, Tailscale operator 1.102.3.

**Spec:** `docs/superpowers/specs/2026-09-03-vault-design.md`

> **SUPERSEDED during execution, in three places.** This plan is kept as a
> historical record only; do not follow the details below without checking
> current truth first.
>
> 1. **Task 4's `vault operator unseal - < "$k"` does not work.** The Vault
>    CLI has no `-` stdin convention, so `-` is sent as the literal key and
>    rejected. The working mechanism is
>    `vault write -format=json sys/unseal key=@"$k"`.
> 2. **`platform/vault/unsealer.yaml` moved to
>    `platform/vault/config/unsealer.yaml`,** and the `vault` Application
>    gained a third source pointing at that directory — without it, the
>    manifest sat in git applied by nothing.
> 3. **The script is inline in the pod template; the ConfigMap is gone.**
>    Editing a ConfigMap does not roll the pods that mount it.
>
> See `platform/vault/README.md` and `docs/troubleshooting.md` entry 9 for
> what actually shipped and why.

## Global Constraints

- **Never run `git push`.** The user reserves all pushes. Commit locally,
  print the exact push command, and wait. Argo CD cannot see an unpushed
  commit.
- **`kubectl` needs a group wrapper on this host:** `sg k3s-admin -c '...'`.
  Nested quoting inside `sg ... -c '...'` is fragile — for anything
  multi-line, write a script to the scratchpad and run that.
- **No credentials in git, ever.** Unseal keys and the root token go to the
  user's password manager and a hand-made Secret. Never ask the user to
  paste them into the conversation, and never print them.
- **Chart pinned to `0.34.1`**, image `hashicorp/vault:2.0.4`.
- **Unseal keys are piped on stdin, never passed as arguments.** Arguments
  are visible in `ps` to every user on the host.
- **Vault runs as `runAsUser: 100`, `runAsGroup: 1000`, `fsGroup: 1000`,
  `runAsNonRoot: true`** — chart defaults, confirmed by rendering.
- **`ProxyClass` and Ingresses live in `infrastructure/ingress/config/`,
  which must contain only valid Kubernetes manifests.**
- **Ingress hostnames are SHORT names** in `spec.tls[0].hosts[0]` — `vault`,
  not `vault.taildf6cd4.ts.net`.
- **Sync waves after this plan:** `argocd` -1, `namespaces` 0,
  `ingress-operator` 2, `vault` 10, `ingress-config` 21.
- Argo CD polls every 3 minutes. Poll for existence before `kubectl wait`,
  which errors immediately on a missing object.

### Task 2: Move `ingress-config` to sync-wave 21

**Files:**
- Modify: `environments/homelab/apps/ingress-config.yaml`
- Modify: `infrastructure/ingress/config/argocd-ingress.yaml`

**Interfaces:**
- Produces: no Application at a wave below 21 depends on ingress health, so
  Task 3's Vault at wave 10 cannot be blocked by it.

**Why.** `ingress-config` sits at wave 3, and a wave gates every wave after
it. An Ingress stays `Progressing` until its controller populates
`status.loadBalancer.ingress`, which depends on the Tailscale control plane.
If that breaks, Vault at wave 10 would never sync at all, with nothing
naming ingress as the cause. This was recorded as a known risk on
2026-09-02 and deferred to this phase.

**The critical property of this change:** it must NOT prune or recreate the
Argo CD Ingress. Changing an Application's own annotation does not touch its
child resources. Pruning and recreating that Ingress is exactly what
produced an orphaned finalizer and a hostname collision on 2026-09-02.

### Task 4: The auto-unseal helper

**Files:**
- Create: `platform/vault/unsealer.yaml`

**Interfaces:**
- Consumes: `http://vault-0.vault-internal:8200` (Task 3).
- Produces: Deployment `vault-unsealer` in namespace `vault`, which unseals
  Vault whenever it is sealed, using Secret `vault-unseal-keys` (created by
  the user in Task 5).

**Security requirements — these are not style preferences:**
- Keys are read from mounted files and piped on **stdin**. Passing a key as
  a command argument exposes it in `ps` to every user on this host.
- Keys are never echoed, logged, or placed in environment variables.
- The Secret volume is `optional: true`, so this Deployment can be applied
  before the Secret exists and simply waits.

- [ ] **Step 1: Create the manifest**

Create `platform/vault/unsealer.yaml`:

```yaml
# Auto-unseal helper for Vault.
#
# Vault OSS has no local-file seal type -- its native auto-unseal is cloud
# KMS or Transit only. So this is a helper that calls the unseal API, not a
# Vault seal. It exists because the alternative is a human entering three
# keys after every reboot, pod reschedule, or k3s restart.
#
# SECURITY POSTURE, stated plainly: the unseal keys live in the same cluster
# as the data they protect. Vault here defends against disk theft, backup
# exposure, and accidental commits to git. It does NOT defend against
# compromise of this host, because an attacker with root gets both the
# ciphertext and the keys. This trade was chosen deliberately.
#
# The keys are piped on stdin, never passed as arguments: command arguments
# are visible in `ps` to every user on this machine.
#
# The Secret mount is optional, so this deploys before the init ceremony has
# happened and waits harmlessly. There is no ordering requirement between
# deploying Vault and initialising it, on first install or on a rebuild.
apiVersion: v1
kind: ConfigMap
metadata:
  name: vault-unsealer
  namespace: vault
data:
  unseal.sh: |
    #!/bin/sh
    # vault status exits 0 unsealed, 2 sealed, 1 on error. No jq needed.
    export VAULT_ADDR="http://vault-0.vault-internal:8200"
    echo "vault-unsealer: watching ${VAULT_ADDR}"
    while true; do
      vault status >/dev/null 2>&1
      rc=$?
      if [ "$rc" -eq 2 ]; then
        echo "vault-unsealer: sealed, attempting unseal"
        for k in /unseal/key1 /unseal/key2 /unseal/key3; do
          [ -s "$k" ] || continue
          vault operator unseal - < "$k" >/dev/null 2>&1 || true
        done
        vault status >/dev/null 2>&1
        if [ $? -eq 0 ]; then
          echo "vault-unsealer: unsealed"
        else
          echo "vault-unsealer: still sealed (uninitialized, or keys absent/wrong)"
        fi
      fi
      sleep 10
    done
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vault-unsealer
  namespace: vault
spec:
  replicas: 1
  selector:
    matchLabels:
      app: vault-unsealer
  template:
    metadata:
      labels:
        app: vault-unsealer
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 100
        runAsGroup: 1000
      containers:
        - name: unsealer
          # Same image as Vault itself -- no third-party unsealer image, so
          # this phase adds exactly one image to the cluster.
          image: hashicorp/vault:2.0.4
          command: ["/bin/sh", "/scripts/unseal.sh"]
          securityContext:

HashiCorp Vault, chart 0.34.1 (Vault 2.0.4), single replica with Raft

Reachable at <https://vault.taildf6cd4.ts.net> from any tailnet device.

## Security posture — read this before trusting it

The unseal keys live in a Kubernetes Secret in the same cluster as the data
they protect. Vault here defends against **disk theft, backup exposure, and
accidental commits to git**. It does **not** defend against compromise of
this host: anyone with root gets both the ciphertext and the keys.

This trade was chosen deliberately so that Vault recovers by itself after a
reboot. It is the common homelab posture, and it is not Vault's usual
security story. Do not describe this Vault as protecting secrets from an
attacker who is already on the machine.

## The init ceremony

Vault comes up sealed and uninitialized. This runs once, by hand.

1. Initialise:

       sg k3s-admin -c 'kubectl -n vault exec vault-0 -- vault operator init -key-shares=5 -key-threshold=3'

2. **Put all five unseal keys and the root token in a password manager
   immediately.** This is the only copy not on this machine. Lose it and the
   data is permanently unreadable.

3. Create the Secret the helper reads, from three of the keys:

       sg k3s-admin -c 'kubectl create secret generic vault-unseal-keys -n vault \
         --from-literal=key1=<key1> --from-literal=key2=<key2> --from-literal=key3=<key3>'

   The names `key1`, `key2`, `key3` are fixed by the helper script. Other
   names give you a helper that runs and silently never unseals.

4. The helper unseals within about ten seconds.

Five shares with a threshold of three buys nothing today, since the cluster
holds a full quorum. It costs nothing either, and it keeps the option of
later withdrawing the keys and splitting custody among people without
re-initialising Vault. Initialising 1-of-1 would close that door.

**The root token is not a permanent credential.** Revoke it once phase 17
establishes real auth methods.

## Backups and recovery

    sg k3s-admin -c 'kubectl -n vault exec vault-0 -- sh -c "VAULT_TOKEN=<token> vault operator raft snapshot save /tmp/v.snap"'
    sg k3s-admin -c 'kubectl -n vault cp vault/vault-0:/tmp/v.snap /tmp/v.snap'
    sudo cp /tmp/v.snap /backups/vault/vault-$(date +%Y%m%d).snap

Scheduled automation is phase 27. This is the verified manual procedure it
will schedule.

**A snapshot alone cannot restore anything.** It is encrypted with Vault's
master key, so restoring into a fresh Vault needs the same unseal keys. The
snapshot and the keys are deliberately kept in different places — snapshots
on disk, keys in a password manager. If they ever end up in the same place,
that place becomes a single point of both total compromise and total loss.

## When Vault will not unseal

    sg k3s-admin -c 'kubectl -n vault logs deploy/vault-unsealer --tail=20'

- "still sealed (uninitialized, or keys absent/wrong)" repeating means
  either the init ceremony has not run, or the Secret is missing or has the
  wrong key names.
- The helper mounts the Secret as optional, so it runs happily with no
  Secret at all. A running helper is not evidence that unsealing works.
- Manual unseal always remains available with the keys from your password
  manager:

      sg k3s-admin -c 'kubectl -n vault exec -it vault-0 -- vault operator unseal'
```
