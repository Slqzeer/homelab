# Penpot Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deploy Penpot as a contract-conformant personal application on the tailnet, signing in through Keycloak, storing state in the cluster's existing PostgreSQL, and answering MCP requests at `https://penpot.taildf6cd4.ts.net/mcp/stream`.

**Architecture:** The upstream `penpot` Helm chart `1.11.3` (appVersion `2.18.3`) is applied by a three-source Argo Application, exactly the shape `platform/vault` already uses: the chart plus `$values/apps/penpot/values.yaml`, plus a second git source for the site manifests no chart owns (VSO objects, NetworkPolicies, the database Job). Penpot's MCP server is **not deployed by hand** — the chart already renders it from the official `penpotapp/mcp` image because `config.flags` defaults to include `enable-mcp`, and the chart wires the frontend to proxy `/mcp/stream` to it. That is why the MCP server gets no Ingress of its own: it has no authentication mechanism, so only the frontend-proxied path is safe.

**Tech Stack:** Kubernetes 1.36 (k3s), Argo CD, HashiCorp Vault + Vault Secrets Operator, Tailscale Kubernetes operator Ingress, PostgreSQL 18.6, Redis, Keycloak (OIDC), Helm chart `penpot` 1.11.3, Python `unittest` for CI gates.

**Spec:** `docs/superpowers/specs/2026-10-07-penpot-design.md`

## Global Constraints

These apply to every task. Copy them verbatim.

- `yamllint --strict -c .yamllint.yaml` gates `apps bootstrap environments infrastructure observability platform .github`. **Every YAML line is at most 100 characters** outside `.github/`.
- Every manifest opens with an explanatory comment block. `document-start` is disabled precisely so this house style survives the gate; do not add `---` at the top.
- No `Secret` manifest is ever committed. Secrets exist only in Vault and as VSO projections.
- Every `VaultStaticSecret` sets `spec.destination.transformation.excludeRaw: true` with `excludes: [" .*"]` (no leading space — the literal is `".*"`) and projects only named keys.
- Tailnet hostname is `taildf6cd4ts.net`-rooted: full name `penpot.taildf6cd4.ts.net`. Ingress `tls.hosts` takes the **short** name only (`penpot`).
- Every Ingress carries `spec.ingressClassName: tailscale` and the `tailscale.com/proxy-group: ingress` annotation.
- The tailnet proxy pool is selected by labels `tailscale.com/parent-resource: ingress` and `tailscale.com/parent-resource-type: proxygroup` in the `tailscale` namespace.
- Child `Application` objects live only in `environments/homelab/apps/`. Site manifests live in `apps/penpot/`.
- Every child Application sets `homelab.io/onboarding-contract: v1`, `homelab.io/owner: personal-applications`, `homelab.io/state: durable`, `backup.homelab.io/restore-runbook: docs/runbooks/penpot-recovery.md`, and `syncPolicy.automated` with `prune: true` and `selfHeal: true`, plus `ServerSideApply=true`.
- `CreateNamespace=true` is forbidden. `bootstrap/namespaces/namespaces.yaml` is the sole namespace owner.
- Sync wave for Penpot is **25**.
- Chart version `1.11.3` is immutable and must satisfy `^\d+\.\d+\.\d+$` because its `repoURL` does not contain `homelab.git`.

## Review Focus

The spec is a vision document; its silence on an input is not permission for that input to break the deployment. These are the five most likely to bite, each pinned to a test in the task that owns the code.

1. **The MCP endpoint reachable without the MCP key.** A reasonable person expects that anything able to write design files requires authentication. If any Ingress, Service or NetworkPolicy admits the MCP Service's ports from the tailnet, an unauthenticated actor can read and modify every design file. Pinned in Task 7.
2. **OIDC endpoints split across two hostnames.** A reasonable person expects one identity provider reachable at one address. `AUTH_URI` must be the tailnet name (the browser follows it) while `TOKEN_URI`, `USER_URI` and `JWKS_URI` must be in-cluster (pods cannot resolve MagicDNS). Getting one of the four wrong yields a redirect loop or an issuer mismatch. Pinned in Task 4.
3. **Redis keys evicted out from under live collaboration.** The shared Redis runs `allkeys-lru`, so Penpot's websocket coordination keys are evictable; a reasonable person expects collaboration state to survive cache pressure. Pinned in Task 4 by an asserted database index of `3`, and in Task 1 by an assertion that the runbook keeps naming `allkeys-lru`, `volatile-lfu` and the dedicated-instance remedy — so the hazard cannot be quietly deleted by a later edit.
4. **A chart upgrade silently moving an unpinned image.** Chart `1.11.3` renders `repository:tag` with no digest field, so a mutable upstream tag is the only thing standing between the cluster and a changed image. A reasonable person expects the deployed digests to be recorded where an upgrade can be checked against them. Pinned in Task 1 by asserting all four digests are in the runbook, in Task 4 by a render step that prints the tags that actually ship, and in Task 9 by recording the gap in the README.
5. **The portal rendering a broken catalogue entry.** `icon` must be one of eight known slugs; an unrecognised one is excluded by the portal, and publishing an Ingress without updating the approved-catalogue test breaks CI for everyone. Pinned in Task 8.

# Penpot, the homelab's design platform, with its MCP server.
#
# Wave 25 -- it genuinely depends on three things below it: PostgreSQL and
# Redis at wave 23 for its data and cache, and Keycloak at wave 24 for OIDC
# sign-in. It joins homelab-portal and tle-dev at 25 rather than opening
# wave 26. Nothing sits behind Penpot, so it gates nothing.
#
# Three sources, the arrangement platform/vault already uses. The chart is
# pinned to an exact version because its repoURL is not this repository, and
# the onboarding contract requires an immutable release revision from any
# external source.
#
# The MCP server is NOT deployed here and needs no Ingress of its own. The
# chart already renders it from the official penpotapp/mcp image, because
# config.flags defaults to include `enable-mcp`, and the frontend proxies
# /mcp/stream to it. Clients use this same hostname:
#   https://penpot.taildf6cd4.ts.net/mcp/stream?userToken=<MCP_KEY>
# That indirection is the security boundary -- the MCP server authenticates
# nobody on its own. See docs/superpowers/specs/2026-10-07-penpot-design.md.
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: penpot
  namespace: argocd
  annotations:
    argocd.argoproj.io/sync-wave: "25"
    homelab.io/onboarding-contract: v1
    homelab.io/owner: personal-applications
    homelab.io/state: durable
    backup.homelab.io/restore-runbook: docs/runbooks/penpot-recovery.md
    homelab.io/chart-version: "1.11.3"
    homelab.io/app-version: "2.18.3"
spec:
  project: default
  sources:
    - repoURL: http://helm.penpot.app
      chart: penpot
      targetRevision: 1.11.3
      helm:
        releaseName: penpot
        valueFiles:
          - $values/apps/penpot/values.yaml
    - repoURL: git@github.com:Slqzeer/homelab.git
      targetRevision: main
      ref: values
    # VSO objects, NetworkPolicies and the database Job are not part of the
    # chart and need a source of their own, exactly as the unsealer does for
    # Vault. path is apps/penpot/config, NOT apps/penpot, which also holds
    # values.yaml: every YAML under a directory `path` is applied as a
    # manifest, and a Helm values file has no kind.
    - repoURL: git@github.com:Slqzeer/homelab.git
      targetRevision: main
      path: apps/penpot/config
  destination:
    server: https://kubernetes.default.svc
    namespace: penpot
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - ServerSideApply=true
```

### Image digests

Chart `1.11.3` renders `image: "{{ .Values.backend.image.repository }}:{{
.Values.backend.image.tag }}"` with no digest field anywhere in its values,
so an image digest cannot be pinned through chart values. This is a
**documented deviation** from the onboarding contract, consistent with every
other chart in this repository: no chart-managed component here pins image
digests. Penpot's images are pinned transitively, by exact chart version
selecting exact image tags.

These digests were resolved from Docker Hub for `2.18.3`. Check them on
every upgrade; a mismatch means an upstream tag moved.

| Image | Digest |
| --- | --- |
| `penpotapp/frontend:2.18.3` | `sha256:bb8abe27d53de84c95597f2c02c0e702b2779971fb0703e543f9ecf183e999f6` |
| `penpotapp/backend:2.18.3` | `sha256:2df1b3440d2a82cc3571db211b4ffdfa2b89ccc910759e8d5e9387fb62971b5c` |
| `penpotapp/exporter:2.18.3` | `sha256:418232d6ca3120b1c2bfde298a56a05a1f41f567cd8494deac3fe7fbc186cfbd` |
| `penpotapp/mcp:2.18.3` | `sha256:5e811e6eeb179d80d8781fb0ffd2991560785d150b3676f1ac5e28d63ba9f7c2` |

## State

| Path | Class | Restored from |
| --- | --- | --- |
| `penpot` database | durable | `pg_dump` / `pg_restore` |
| `penpot-assets` PVC | durable | filesystem copy |
| `api-secret-key` | secret-derived | Vault; rotation invalidates sessions |
| `oidc-client-secret` | secret-derived | Vault; the registration Job re-applies it |
| `mcp-key` | secret-derived | Penpot Integrations; regenerating revokes the old key |
| Redis database 3 | reconstructible | nothing; cache and coordination only |

## Ceremonies

Three steps happen outside git. None is reproduced by a cluster rebuild.

1. **Vault seed.** Run `platform/vault/configure-vault.sh`. It seeds
   `homelab/penpot` (`postgres-password`, `api-secret-key`,
   `oidc-client-secret`) and `homelab/penpot/data` (`password`). The Redis
   URI is not seeded: VSO renders it from the shared Redis password at
   `homelab/redis`, so rotating that path rolls Penpot with no re-run.
2. **MCP key.** In Penpot: *Your account → Integrations → MCP Server* →
   enable, then generate a key. It is shown **once** and is not
   recoverable. Store it in a password manager and seed it into Vault at
   `homelab/penpot` as `mcp-key`.

   | Field | Value |
   | --- | --- |
   | Issued | _recorded in Task 10, step 6_ |
   | Expires | _recorded in Task 10, step 6_ |

   Do not leave these as an unlabelled blank. `platform/registry/README.md`
   has exactly that shape for its GHCR token and the root README lists it as a
   known gap; a blank nobody can attribute is how the GHCR expiry became
   unknown to everyone but its issuer. Task 10 owns both fields.

   The expiry date must be filled in. An expired key surfaces as an MCP
   client that cannot connect, with nothing in the cluster naming expiry —
   the same delayed, misleading failure mode as the GHCR token.
3. **Keycloak client.** The `penpot` OIDC client is reconciled by the
   `PostSync` hook in `platform/keycloak/config/client-registration.yaml`,
   not by hand. It reads its secret from Vault, so re-running the hook is
   how a rotated secret reaches Keycloak.

## Backup and restore

Local-path storage is single-node and is **not** a backup. Nothing here is
backed up automatically.

```bash
# Database. Consistent because pg_dump takes a snapshot.
kubectl -n databases exec statefulset/postgres -- \
  pg_dump -U postgres -d penpot --format=custom --file=/tmp/penpot.dump
kubectl -n databases cp statefulset/postgres:/tmp/penpot.dump ./penpot.dump

# Assets.
kubectl -n penpot cp statefulset/penpot-assets:/opt/data/assets ./penpot-assets
```

Restore order is assets first, then the database: the database stores asset
references, so it is meaningless without the files behind it.

```bash
kubectl -n databases cp ./penpot.dump statefulset/postgres:/tmp/penpot.dump
kubectl -n databases exec statefulset/postgres -- \
  pg_restore -U postgres -d penpot --clean --if-exists /tmp/penpot.dump
```

## Upgrade

1. Read the chart's changelog and confirm the new `appVersion`.
2. Resolve the new image digests and add them to the table above.
3. Take a database dump and an assets copy first.
4. Bump `targetRevision` in `environments/homelab/apps/penpot.yaml` and both
   version annotations.
5. Watch the backend run its migrations before declaring success. The
   backend owns the schema and migrates on start.
6. Roll back by reverting the chart version **and** restoring the dump if
   migrations were not backward compatible.

## Rollback

Stateful rollback has a database-compatibility caveat the onboarding
contract requires be accounted for: a Penpot downgrade may need the
pre-upgrade dump restored, because the backend's migrations are not
guaranteed reversible. Chart-only rollback (values, flags, resources) needs
no data restore.

## Retirement

Disable portal publication first, then take a final dump and assets copy.
Revoke the Keycloak client, remove the child Application, then inspect the
`penpot-assets` PVC before removing the namespace. Deleting the namespace
cascades to the PVC and is not reversible.

## Known gaps

- **The shared Redis eviction policy is not Penpot's recommendation.** This
  cluster's cache is the `redis:8.2-alpine` StatefulSet in `databases`, running
  `maxmemory 128mb` with `maxmemory-policy allkeys-lru`; Penpot documents
  `volatile-lfu`. Under `allkeys-lru` Penpot's websocket coordination keys are
  evictable, and evicting one degrades live collaboration rather than merely
  slowing a cache. `maxmemory` and the policy are cluster-wide and cannot be
  varied per client. Watch `evicted_keys` on the Redis instance; if Penpot
  evicts under real use the fix is a separate `valkey/valkey` StatefulSet for
  Penpot — the arrangement `apps/tle-dev/config/datastores.yaml` already
  demonstrates — not a change to the shared cache.
- **No Penpot series reach Grafana Cloud.** No component of Penpot 2.18.3
  exposes a Prometheus endpoint, so there is no ServiceMonitor for it. The
  exporter is the trap: its name suggests it exports metrics, but port 6061
  serves `POST /api/export` and `/readyz` for a headless-browser renderer.
  Health is visible only through the cluster-level `kube_pod_*` and
  `kube_deployment_*` series already in the allowlist.
- **The admin console is disabled.** `enable-admin-console` is absent from
  `config.flags`; it is a fifth deployment on port 3000 that a personal
  installation does not need. Re-enabling it requires a NetworkPolicy rule.

Replace the whole block with this version, which carries the origin per entry:

```sh
    # This is the entire mutation allowlist. Query errors and duplicate IDs
    # abort the hook; neither may be interpreted as an absent client.
    # Arguments are positional: client_id, secret env var, display name,
    # origin, callback path, logout path. The origin and the OIDC callback
    # path are per entry, never constants inside this function: Penpot's
    # callback is /api/oauth/redirect, which is NOT the portal's
    # /auth/callback, and a shared constant would rewrite the portal's.
    reconcile_client() {
      client_id=$1 secret_var=$2 display_name=$3 origin=$4
      callback=$5 logout_path=$6
      # jq reads the secret, not the shell: $secret_var (the NAME) goes into
      # argv and the value comes back out of jq's own environment. The value
      # never becomes a process argument of anything: --arg is handed the
      # name only, and handing it the value instead would put the secret in
      # every argument list. A coreutils environment reader would do the same
      # job, but it is used nowhere else in this repository and cannot be
      # assumed present in the Keycloak image, where its absence would abort
      # the hook under set -e. jq is already a hard dependency below; if it
      # were missing this hook could not work at all, so this adds no new way
      # to fail.
      secret_value=$("$JQ" -nr --arg env_name "$secret_var" 'env[$env_name]')
      clients_json=$("$KCADM" get clients -r homelab \
        -q clientId="$client_id" --fields id,clientId \
        --config /tmp/kcadm.config)
      client_uuid=$(printf '%s' "$clients_json" | "$JQ" -er \
        --arg client_id "$client_id" \
        '[.[] | select(.clientId == $client_id)] |
         if length == 0 then ""
         elif length == 1 then .[0].id
         else error("duplicate client ID: " + $client_id) end')

      desired_json=$("$JQ" -n \
        --arg client_id "$client_id" \
        --arg name "$display_name" \
        --arg redirect "${origin}${callback}" \
        --arg origin "$origin" \
        --arg logout "${origin}${logout_path}" \
        --arg env_name "$secret_var" \
        '{clientId: $client_id,
          name: $name,
          protocol: "openid-connect",
          enabled: true,
          publicClient: false,
          clientAuthenticatorType: "client-secret",
          standardFlowEnabled: true,
          implicitFlowEnabled: false,
          directAccessGrantsEnabled: false,
          serviceAccountsEnabled: false,
          redirectUris: [$redirect],
          webOrigins: [$origin],
          attributes: {"post.logout.redirect.uris": $logout},
          secret: env[$env_name]}')

      # Project only fields this hook owns. Keycloak adds server-side fields
      # and other operators may set unrelated client fields. Never print the
      # secret-bearing response or desired body during comparison.
      canonical() {
        "$JQ" -cS '
          del(.secret) |
          {clientId, name, protocol, enabled, publicClient,
           clientAuthenticatorType, standardFlowEnabled,
           implicitFlowEnabled, directAccessGrantsEnabled,
           serviceAccountsEnabled, redirectUris, webOrigins,
           attributes: {"post.logout.redirect.uris":
                        .attributes["post.logout.redirect.uris"]}}
        '
      }
      desired_public=$(printf '%s' "$desired_json" | canonical)

      if [ -z "$client_uuid" ]; then
        if ! printf '%s' "$desired_json" | "$KCADM" create clients -r homelab \
            --config /tmp/kcadm.config -f - >/dev/null 2>&1; then
          echo "$client_id client create failed" >&2
          exit 1
        fi
        echo "created $client_id client"
        clients_json=$("$KCADM" get clients -r homelab \
          -q clientId="$client_id" --fields id,clientId \
          --config /tmp/kcadm.config)
        client_uuid=$(printf '%s' "$clients_json" | "$JQ" -er \
          --arg client_id "$client_id" \
          '[.[] | select(.clientId == $client_id)] |
           if length == 1 then .[0].id
           else error("created client lookup was not unique") end')
      else
        current_json=$("$KCADM" get "clients/$client_uuid" -r homelab \
          --config /tmp/kcadm.config)
        current_public=$(printf '%s' "$current_json" | canonical)
        current_secret_json=$("$KCADM" get "clients/$client_uuid/client-secret" \
          -r homelab --config /tmp/kcadm.config)
        current_secret=$(printf '%s' "$current_secret_json" | "$JQ" -r '.value // ""')
        if [ "$current_public" = "$desired_public" ] && \
           [ "$current_secret" = "$secret_value" ]; then
          echo "$client_id client already current"
        else
          # --merge retains unrelated client fields. This body carries no
          # defaultClientScopes, so client scopes are not touched here at
          # all: the explicit scope loop below is their only owner, and it
          # adds what is missing rather than replacing the whole mapping.
          if ! printf '%s' "$desired_json" | "$KCADM" update "clients/$client_uuid" \
              -r homelab --config /tmp/kcadm.config --merge -f - >/dev/null 2>&1; then
            echo "$client_id client update failed" >&2
            exit 1
          fi
          echo "updated $client_id client"
        fi
      fi

      # Client scope mappings are a separate Keycloak resource. Add only the
      # required defaults; preserve any other scopes operators attached.
      current_scopes=$("$KCADM" get "clients/$client_uuid/default-client-scopes" \
        -r homelab --config /tmp/kcadm.config)
      available_scopes=
      for scope_name in profile email groups; do
        if printf '%s' "$current_scopes" | "$JQ" -e \
            --arg name "$scope_name" 'any(.[]; .name == $name)' >/dev/null; then
          continue
        fi
        if [ -z "$available_scopes" ]; then
          available_scopes=$("$KCADM" get client-scopes -r homelab \
            --config /tmp/kcadm.config)
        fi
        scope_uuid=$(printf '%s' "$available_scopes" | "$JQ" -er \
          --arg name "$scope_name" \
          '[.[] | select(.name == $name)] |
           if length == 1 then .[0].id
           else error("required client scope missing or duplicated") end')
        if ! "$KCADM" update "clients/$client_uuid/default-client-scopes/$scope_uuid" \
            -r homelab --config /tmp/kcadm.config >/dev/null 2>&1; then
          echo "$client_id default scope update failed" >&2
          exit 1
        fi
        current_scopes=$("$KCADM" get "clients/$client_uuid/default-client-scopes" \
          -r homelab --config /tmp/kcadm.config)
        if ! printf '%s' "$current_scopes" | "$JQ" -e \
            --arg name "$scope_name" 'any(.[]; .name == $name)' >/dev/null; then
          echo "$client_id default scope verification failed" >&2
          exit 1
        fi
      done
      # Verify the complete required set, not merely the most recent add.
      for scope_name in profile email groups; do
        if ! printf '%s' "$current_scopes" | "$JQ" -e \
            --arg name "$scope_name" 'any(.[]; .name == $name)' >/dev/null; then
          echo "$client_id default scope verification failed" >&2
          exit 1
        fi
      done
    }

    reconcile_client homelab-portal PORTAL_CLIENT_SECRET "Homelab Portal" \
      https://portal.taildf6cd4.ts.net /auth/callback /auth/logout
    # Penpot does expose POST /api/logout, but nothing a browser can be
    # redirected to, and Keycloak's post.logout.redirect.uris is a browser
    # GET. Hence the empty path, giving the trailing "/" that lands on the
    # application root rather than a logout route.
    reconcile_client penpot PENPOT_CLIENT_SECRET "Penpot" \
      https://penpot.taildf6cd4.ts.net /api/oauth/redirect /
```

    @staticmethod
    def pod_set(selector):
        # The Penpot components a podSelector picks out: "*" for every pod,
        # otherwise the `app` values it names via matchLabels or `app In`.
        if selector == {}:
            return "*"
        labels = selector.get("matchLabels", {})
        if labels:
            return frozenset({labels["app"]})
        expression, = selector["matchExpressions"]
        assert (expression["key"], expression["operator"]) == ("app", "In"), expression
        return frozenset(expression["values"])

    @staticmethod
    def peer_key(peer):
        # (namespace or None for "this namespace", labels as sorted pairs).
        # A namespace-wide peer has labels None, so it can never compare
        # equal to a pod-scoped one.
        namespace = None
        if "namespaceSelector" in peer:
            namespace = peer["namespaceSelector"]["matchLabels"][
                "kubernetes.io/metadata.name"]
        labels = peer.get("podSelector", {}).get("matchLabels")
        return namespace, tuple(sorted(labels.items())) if labels is not None else None

    def policy_flows(self, policy):
        # Every (direction, selected pods, peer, port) a policy grants.
        flows = set()
        selected = self.pod_set(policy["spec"]["podSelector"])
        for direction, peers_key in (("ingress", "from"), ("egress", "to")):
            for rule in policy["spec"].get(direction, []):
                # No rule may omit its peers or ports: either means "any".
                self.assertTrue(rule.get(peers_key), policy["metadata"]["name"])
                self.assertTrue(rule.get("ports"), policy["metadata"]["name"])
                for peer in rule[peers_key]:
                    for port in rule["ports"]:
                        self.assertNotIn("endPort", port)
                        flows.add((direction, selected, self.peer_key(peer),
                                   port.get("protocol", "TCP"), port["port"]))
        return flows

spec:
  ingressClassName: tailscale
  defaultBackend:

      name: penpot
      port:
        name: http
  tls:

- [ ] **Step 6: Verify MCP end to end**

1. In Penpot: *Your account → Integrations → MCP Server* → enable, generate a key.
2. Store it in a password manager, then seed Vault. This must be a **`kv
   patch`**, not a `kv put`: `homelab/penpot` already carries
   `postgres-password`, `postgres-username`, `api-secret-key` and
   `oidc-client-secret`, and a KV v2 `put` replaces every key at the path, so a
   `put` would delete all four and break both the database login and OIDC.

   This runs **inside the Vault pod**, where the `vault` CLI is
   authenticated. Paste the key at the `MCP key:` prompt:

   ```sh
   sg k3s-admin -c 'kubectl -n vault exec -it vault-0 -- sh -c '"'"'
     umask 077
     MCP_KEY_FILE=$(mktemp)
     trap "rm -f \"$MCP_KEY_FILE\"" EXIT
     printf "MCP key: "
     read -r MCP_KEY < /dev/tty && printf "\n"
     printf %s "$MCP_KEY" >"$MCP_KEY_FILE"
     unset MCP_KEY
     vault kv patch homelab/penpot mcp-key=@"$MCP_KEY_FILE"
     vault kv get -field=mcp-key homelab/penpot >/dev/null && echo "mcp-key stored"
   '"'"''
   ```

   The key is read from the pod's terminal and written with `printf %s`, so
   the file holds the key with no trailing newline -- a heredoc would store
   one, and Vault would keep it as part of the value. Only the filename
   becomes an argument; a value on a command line is visible in `ps`. This is
   the same snippet as `docs/runbooks/penpot-recovery.md`.

3. Point an MCP client at

- [ ] **Step 8: Verify secret rotation**

Change the database password in Vault, wait for the refresh, and confirm the
backend reconnects.

The password lives at **two** paths, and the rotation must change **both**,
because the Job applies `homelab/penpot/data/password` to the role while the
chart authenticates with `homelab/penpot/postgres-password`. Changing only one
leaves Penpot unable to connect, and `configure-vault.sh` will then refuse to
run until the two match again -- it compares them and will not choose for you:

```bash
sg k3s-admin -c 'kubectl -n vault exec -i vault-0 -- sh' <<'IN_POD'
umask 077
NEW_PW_FILE=$(mktemp)
trap 'rm -f "$NEW_PW_FILE"' EXIT
head -c 256 /dev/urandom | tr -dc 'A-Za-z0-9' | head -c 32 >"$NEW_PW_FILE"
# patch, never put: a put replaces every other key at the path.
vault kv patch homelab/penpot      postgres-password=@"$NEW_PW_FILE"
vault kv patch homelab/penpot/data password=@"$NEW_PW_FILE"
IN_POD
```

Note the same applies to the OIDC client secret, which lives at
`homelab/penpot/oidc-client-secret` and `homelab/penpot-client/clientSecret`.
